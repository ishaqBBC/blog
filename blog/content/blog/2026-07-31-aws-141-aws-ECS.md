## TLDR

Amazon Elastic Container Service (ECS) is AWS's native container orchestration platform for running Docker containers. ECS offers two launch types: EC2 (manage your own infrastructure) and Fargate (serverless). The service integrates with IAM roles for security, supports various load balancers for traffic distribution, and can persist data using Amazon EFS. Fargate is the recommended approach for most use cases due to its serverless nature and simplified management.

## Introduction

Container orchestration has become essential for modern cloud infrastructure. After exploring [Docker](https://magicishaqblog.netlify.app/2026-07-24-aws-140-docker-introduction/) in the previous post, it's time to examine Amazon Elastic Container Service (ECS)—AWS's container orchestration platform. ECS handles the deployment, management, and scaling of containerised applications. It offers two launch types and integrates with the broader AWS ecosystem.

## What Is Amazon ECS?

Amazon ECS (Elastic Container Service) is AWS's solution for running Docker containers at scale. When deploying containers using ECS, you're launching **ECS Tasks** within an **ECS Cluster**.

Think of an ECS Cluster as the fundamental infrastructure unit. It's a logical grouping of resources that hosts your containerised applications. What goes into this cluster? That depends on your launch type.

![image of the ECS](/blog/src/images/141/141-1.png)

## EC2 Launch Type

The EC2 Launch Type is the traditional approach to running containers on AWS. Your ECS Cluster consists of [EC2 instances](https://magicishaqblog.netlify.app/2023-02-24-aws-10-EC2/) that you provision and maintain.

### How It Works

With the EC2 Launch Type, you're responsible for managing the underlying infrastructure. Your ECS Cluster contains multiple EC2 instances, each running the **[ECS Agent](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_agent.html)**—a piece of software that does the heavy lifting.

The ECS Agent registers each EC2 instance with the Amazon ECS service and your chosen cluster. Once registered, AWS can orchestrate container placement.

When you start ECS tasks, AWS determines where to place each Docker container across your EC2 instances. New containers get distributed across your infrastructure automatically. You can start and stop tasks whenever needed—AWS handles the placement.

Here's the trade-off: Docker containers run on EC2 instances you've provisioned in advance. You get full control over the infrastructure, but you're also responsible for capacity planning, patching, and monitoring.
![image of the ECS](/blog/src/images/141/141-2.png)

## Fargate Launch Type

Fargate changes how containers are deployed on AWS. You launch Docker containers without provisioning infrastructure—no EC2 instances to manage.

### Serverless Container Deployment

Fargate is often called serverless, though that's not entirely accurate. Servers exist behind the scenes—AWS just manages them entirely. You don't see them, configure them, or maintain them.

With Fargate, your ECS Cluster is a logical construct. You create a **task definition** describing your ECS tasks—the Docker image, CPU and RAM requirements, networking configuration, and other parameters.

AWS runs these tasks based on your specifications. Need to run a new Docker container? It just runs. No EC2 instance appears in your account. The infrastructure is completely abstracted.

### Scaling with Fargate

Scaling with Fargate is straightforward. To handle increased load, increase the number of tasks. No need to provision EC2 instances, configure auto-scaling groups, or manage capacity.

This simplicity makes Fargate the preferred choice for most scenarios. AWS certification exams favour Fargate-based solutions, which reflects its position as the modern approach to container orchestration.

## IAM Roles for ECS Tasks

Security and access control in ECS work through IAM roles. The structure differs between EC2 and Fargate launch types.

### EC2 Instance Profile

With the EC2 Launch Type, you create an **EC2 Instance Profile**. The ECS Agent running on each EC2 instance uses this role exclusively.

The EC2 Instance Profile gives the ECS Agent permissions to:

- Make API calls to the ECS service to register the instance
- Send container logs to CloudWatch Logs
- Pull Docker images from Amazon Elastic Container Registry (ECR)
- Retrieve sensitive data from AWS Secrets Manager or Systems Manager Parameter Store

This role operates at the infrastructure level, letting the ECS Agent do its job.

![instance profile](/blog/src/images/141/141-3.png)

### ECS Task Roles

Beyond the EC2 Instance Profile (when applicable), each ECS task gets its own **ECS Task Role**. This works for both EC2 and Fargate.

ECS Task Roles define what AWS services your containerised application can access. Different tasks can have different roles for fine-grained access control.

For example:

- **Task A** has a role permitting API calls to Amazon S3—it can read and write objects to specific buckets
- **Task B** has a role permitting API calls to Amazon DynamoDB—it can query and update tables

You define the task role in the task definition. This separation—infrastructure permissions versus application permissions—provides solid security while maintaining flexibility.

## Load Balancer Integration

Container applications often need exposure as HTTP or HTTPS endpoints. ECS integrates with AWS load balancing services to distribute traffic across tasks.

### Application Load Balancer (ALB)

The Application Load Balancer is recommended for most ECS deployments. Whether using EC2 or Fargate, an ALB routes incoming requests to your ECS tasks.

The ALB operates at Layer 7 (application layer), supporting advanced routing based on URL paths, hostnames, query parameters, and headers. Perfect for microservices architectures where different services use different routes.

Users connect to the ALB, which forwards requests to the appropriate ECS tasks in your cluster.

### Network Load Balancer (NLB)

The Network Load Balancer suits specific scenarios:

- **High throughput**: Handling millions of requests per second
- **High performance**: When ultra-low latency matters
- **AWS PrivateLink**: Exposing services privately to other VPCs or accounts

The NLB operates at Layer 4 (transport layer), routing traffic based on IP protocol data without inspecting packet contents.

### Classic Load Balancer

The Classic Load Balancer is the older generation of AWS load balancing. It's still available but not recommended for new deployments.

Importantly, Classic Load Balancer doesn't support Fargate. If you're using Fargate (the recommended approach), stick with Application Load Balancer or Network Load Balancer.

## Data Persistence with Amazon EFS

Containers are ephemeral by nature. When a task stops, data stored in its container filesystem vanishes. For applications needing persistent storage, ECS supports mounting file systems onto tasks.

### Using Amazon EFS with ECS

Amazon Elastic File System (EFS) is a network file system that integrates with ECS. It works with both EC2 and Fargate launch types.

When you mount an EFS file system onto your ECS tasks, they can read and write shared data. Tasks in any availability zone can access the same file system simultaneously—enabling data sharing and persistence across your infrastructure.

### The Serverless Combination

Pairing Fargate with Amazon EFS creates a fully serverless container environment. Fargate removes EC2 instance management, while EFS provides serverless, scalable file storage.

Both services use pay-as-you-go pricing. You provision capacity as needed without managing servers. This combination works well for applications needing persistent, multi-AZ shared storage for containers.

### Use Cases

Common scenarios for using EFS with ECS:

- **Shared configuration**: Multiple tasks accessing the same config files
- **Content management**: Web apps storing uploaded media
- **Data processing pipelines**: Tasks reading input and writing output to shared storage
- **Stateful applications**: Apps needing file-based persistence across container restarts

The advantage? Data persists independently of any container's lifecycle while remaining accessible to all tasks.

## Conclusion

Amazon ECS provides a robust platform for running containerised applications on AWS. Choosing between EC2 Launch Type and Fargate depends on your requirements, though Fargate's serverless approach makes it the preferred option for most applications.

ECS integrates with IAM for security, supports multiple load balancer types for traffic distribution, and enables persistent storage through Amazon EFS. Understanding these components and their interactions is essential for designing resilient, scalable containerised architectures on AWS.
