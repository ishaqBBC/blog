## TLDR

[Amazon Elastic Container Registry (ECR)](https://docs.aws.amazon.com/ecr/) is AWS's managed registry for Docker and other OCI container images. It gives you a private place to store images in your AWS account, or a public place to share them through the [Amazon ECR Public Gallery](https://gallery.ecr.aws/). ECR works closely with [Amazon ECS](https://docs.aws.amazon.com/ecs/) and includes image scanning, tags, lifecycle policies, and access control through IAM.

## Introduction

The previous post introduced [Amazon ECS](https://magicishaqblog.netlify.app/2026-07-31-aws-141-aws-ECS/), AWS's service for running containers. ECS can start and manage containers, but it still needs an image to run. That image has to live somewhere that ECS can reach.

Many developers begin with [Docker Hub](https://hub.docker.com/). It is a useful public registry, but production applications often need a registry that is private, close to the rest of the AWS environment, and controlled by the same identity and security policies. That is where ECR fits.

![logo of ECR](/blog/src/images/149/149-1.png)

## What Is Amazon ECR?

Amazon ECR is a managed container registry. A registry stores container images and makes them available to the systems that need to run them. In ECR, images are organised into repositories.

A repository might contain several versions of the same application:

```text
my-api:latest
my-api:1.4.0
my-api:production
```

The part after the colon is an **image tag**. Tags make images easier to identify, although a tag can be moved to another image. For deployments that must be repeatable, an image digest is more precise because it identifies the exact image content.

AWS manages the registry service for you, while the image data is stored using AWS infrastructure. You do not need to provision a file server or maintain the registry software yourself. The [Amazon ECR User Guide](https://docs.aws.amazon.com/AmazonECR/latest/userguide/what-is-ecr.html) explains the service's supported image formats and repository model.

## Private and Public Repositories

ECR has two main publishing models.

A **private repository** is intended for images used by your organisation. Access is controlled through IAM and repository policies. You can allow ECS, CI/CD systems, or other AWS accounts to pull an image without making that image public.

A **public repository** is designed for sharing images with anyone. Images can be published to the [Amazon ECR Public Gallery](https://gallery.ecr.aws/), where users can discover and pull them. Public does not mean anonymous control: publishing still requires the appropriate AWS account permissions.

For most application deployments, a private repository is the usual choice. Public repositories make sense for open-source projects, base images, and tools that are deliberately distributed to a wider audience.

## Pushing an Image to ECR

The normal workflow is short. First, create a repository, authenticate Docker to the ECR registry, tag the local image with the repository URI, and push it.

The AWS CLI documentation provides the exact command for obtaining a temporary authentication token with [`get-login-password`](https://docs.aws.amazon.com/cli/latest/reference/ecr/get-login-password.html). A typical workflow looks like this:

```bash
aws ecr create-repository --repository-name my-api

aws ecr get-login-password --region eu-west-1 \
  | docker login --username AWS --password-stdin <account-id>.dkr.ecr.eu-west-1.amazonaws.com

docker tag my-api:latest <account-id>.dkr.ecr.eu-west-1.amazonaws.com/my-api:1.0.0
docker push <account-id>.dkr.ecr.eu-west-1.amazonaws.com/my-api:1.0.0
```

Replace the Region, account ID, repository name, and tag with values from your environment. The complete process is documented in [Pushing a Docker image to Amazon ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html).

The registry URI is part of the image name. That is how Docker knows that the image should be sent to ECR rather than to Docker Hub.

## How ECR Works with ECS

The relationship between the two services is easy to remember:

- **ECR stores the image.**
- **ECS runs the container created from the image.**

In an [ECS task definition](https://magicishaqblog.netlify.app/2026-08-27-aws-145-ECS-task-definitions/), the container image is identified by its ECR URI. When ECS starts a task, the ECS agent or Fargate infrastructure pulls that image and starts the container.

The identity used to pull the image depends on the launch type. With Fargate, the **task execution role** normally grants ECS permission to retrieve the image. With the EC2 launch type, the container instance's **EC2 instance role** needs the permissions required by the ECS agent. AWS documents the required permissions in the [AmazonECSTaskExecutionRolePolicy](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AmazonECSTaskExecutionRolePolicy.html) and the [ECS container instance IAM role](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/instance_IAM_role.html) guidance.

This is why ECR pull failures are often IAM problems rather than Docker problems. If a task cannot start because it cannot pull its image, check the Region, repository URI, network access, and the role policy before changing the task definition. The [ECS hands-on task definition post](https://magicishaqblog.netlify.app/2026-09-03-aws-146-ECS-task-definition-hands-on/) shows where the execution role appears in an ECS configuration.

## Security and Image Scanning

ECR repositories are protected by IAM. An identity must have permission to perform actions such as describing repositories, obtaining an authorization token, and downloading image layers. Repository policies can also grant access to another AWS account.

ECR supports [image scanning](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-scanning.html) to identify known vulnerabilities in operating-system packages and other components. Scanning does not make an image safe by itself. It gives the team information to use when deciding whether to rebuild, update a dependency, or stop a deployment.

A sensible pipeline builds the image, scans it, and promotes only an approved version. It should also avoid placing passwords or access keys inside an image. Secrets belong in services such as [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html), with access granted to the running task rather than baked into the image.

## Tags, Digests, and Lifecycle Policies

Tags are useful for people. A tag such as `staging` or `1.0.0` makes a deployment easy to recognise. A digest is useful for systems because it points to immutable image content. In a production deployment, using a digest or a carefully managed release tag reduces the risk of silently running a different image than the one that was tested.

Repositories can accumulate old images quickly. ECR [lifecycle policies](https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html) can expire untagged images or remove older revisions according to rules you define. This keeps the repository manageable and can reduce storage costs. Set the policy deliberately: an image that is no longer used by ECS may still be needed for a rollback.

## The Bigger Picture

ECR is one piece of the container workflow:

1. A developer writes a Dockerfile and builds an image.
2. The image is pushed to an ECR repository.
3. A task definition refers to that image.
4. ECS places the task on Fargate or an EC2 container instance.
5. IAM controls who can push and pull the image.
6. Scanning and lifecycle policies help maintain the repository over time.

The earlier [Docker introduction](https://magicishaqblog.netlify.app/2026-07-24-aws-140-docker-introduction/) covers the first step. The [ECS task placement post](https://magicishaqblog.netlify.app/2026-09-09-aws-147-task-placement/) covers what happens after ECS has a task to run.

## Conclusion

Amazon ECR is more than a place to upload Docker images. It is the registry that connects the image-building process with the ECS runtime. Private repositories keep application images under account control, IAM decides who may use them, scanning highlights known vulnerabilities, and lifecycle policies help remove images that are no longer useful.

For the exam and for day-to-day AWS work, the central idea is simple: ECR stores container images, while ECS runs them. When an ECS task cannot start, check that the image exists in the expected Region and that the execution role or EC2 instance role can pull it.
